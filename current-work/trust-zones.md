# Trust Zones

A modular on-chain agreement substrate for AI agents, built at [The Synthesis](the-synthesis.md) (March 13–22, 2026). **Hackathon project, not a peer-reviewed paper, not a shipped industry product.**

**Takeaway for this landscape:** the closest built analogue to LightForest's principal/agent contract is not a referral paper — it is an agreement substrate that composes deterministic constraints with post-hoc, incentive-backed obligations and a portable reputation record. Trust Zones is the most complete public example found so far. It is not a referral tree and does not solve multilevel attribution; the useful piece is how non-deterministic rules get teeth (slashable stake, adjudication, ERC-8004 feedback).

- **Summary:** Each agreement is a smart contract; each party gets a Trust Zone (an ERC-7579 smart account) holding that party's role. Terms split along two axes: *deterministic* constraints and permissions, self-enforcing via ERC-7579 hooks and ERC-6909 resource tokens, versus *non-deterministic* responsibilities and directives, which need post-hoc evaluation by an adjudicator. Incentive modules — staked USDC collateral, slashable on violation, plus protocol-level ERC-8004 reputation feedback written when an agreement closes — give the non-deterministic rules consequences. A mechanism compiler turns human-readable terms into on-chain proposals. The Temptation Game demo on Base mainnet granted an agent real permissions (tweet via an ERC-8128-gated proxy; withdraw USDC from a vault) while a directive said not to withdraw, with a slashable bond and reputation at stake. The monorepo has 11 packages (Solidity contracts, TypeScript SDK, compiler, Ponder indexer, agents, CLI, viz, x402 MCP service, Bonfires integration). Author-reported test count: 539 (394 contract, 56 SDK, 23 compiler, 36 indexer, 30 E2E) **(not re-run here)**.

- **Implication for referralTree:** Closest public build of LightForest's "standing terms, then work, then evaluation" loop, including slashable bonds and a portable reputation record (ERC-8004) that feeds into later terms — the same shape as ongoing referrer liability, just applied to an agent agreement rather than a referral edge. It does not implement a referral tree, a geometric split, or Sybil-proof payouts. Treat it as a design reference for how agents could take on standing opportunities (and for bonding + adjudication as teeth), not as a payout-rule precedent. The x402-gated MCP service is a possible payment integration point next to [agent-x402-attribution](../competitors/agent-x402-attribution.md).
