# Agent and x402 attribution

Referral/attribution for machine-to-machine payments. This is where LightForest's "Work for Agents" framing competes most directly: these projects move agent payments, LightForest publishes the terms agents work under and records the outcome.

### Split402
- **What:** referral commissions for x402-paid APIs. <https://github.com/split402protocol/splitx402>
- **Mechanism:** an agent attaches a signed referral claim to a normal x402 USDC payment; the merchant receives the gross payment; Split402 records commission liability (campaign bps, optional protocol fee as % of commission), verifies settlement on-chain, then pays accrued commissions later in batches from a merchant-controlled wallet. Its README says the MVP does **not** split the x402 payment atomically.
- **Traction:** none public.
- **vs referralTree:** single-level, deferred, off-chain ledger of liabilities; referralTree pays a multilevel chain atomically in one call with on-chain receipts.

### IETF AREF draft (draft-stone-aref-00)
- **What:** *Agent Referral and Escrow Framework*, individual Internet-Draft by B. Stone (SwarmSync.AI), published 2026-09-04, expires 2027-03-08, intended status Informational, not IETF-endorsed. <https://datatracker.ietf.org/doc/draft-stone-aref/>
- **Mechanism:** Ed25519-signed attribution proofs for referral chains of arbitrary depth; a `SwarmSync-Referrer` HTTP header binding a referrer to an escrow at hold time; commission vests only when escrow is RELEASED (not on enrollment); a unified settlement-finality signal across Stripe Connect and x402; `swarm_meta` JSON for propagating referral codes between agents.
- **Traction:** still at -00 as of 2026-11-09 (datatracker API).
- **vs referralTree:** a protocol spec for the same problem space (multi-hop agent referral) with escrow-based vesting. referralTree has a deployed, audited contract and a fixed split rule; AREF leaves the split to the platform. Watch for -01 and adopters.

### x402 builder codes (ERC-8021) and PR #3666
- **What:** ERC-8021 "Transaction Attribution" appends a data suffix to calldata identifying the builder/app (Base Builder Codes: <https://docs.base.org/specifications/builder-codes/overview>; EIP text <https://eip.tools/eip/8021>). The x402 `builder-code` extension uses ERC-8021 Schema 2.
- **PR #3666** (<https://github.com/x402-foundation/x402/pull/3666>), merged 2026-10-06: adds facilitator-authored settlement metadata `m` to the builder-code extension: only the facilitator writes it (client-supplied `m` is ignored), keys prefixed `x402`, deterministic CBOR ≤ 65,535 bytes; TS and Go SDK support. No scheme emits metadata yet; a follow-up will move batch-settlement charge counts into `m.x402ChargeCounts`.
- **Traction:** x402 is a Coinbase-originated standard. Usage baseline from Circle Research (Anduin, arXiv:2611.05586): 66,073,201 x402 settlements across 16 chains from Mar 23 to Aug 26, 2026, 162,882 buyers, 50,390 providers, $6.1M volume, median payment $0.01; the paper puts the second-largest machine-payment protocol (MPP) at ≈$270K.
- **vs referralTree:** attribution *tagging* (who drove this tx), not payout. Complementary: an ERC-8021 code could be the evidence an oracle uses to sign `rewardRoots`, and facilitator metadata gives a trusted place to carry it.

### x402 multi-payee splits on the `exact` scheme (spec PR #3221, merged 2026-10-26)
- **What:** optional extension letting one x402 payment be split atomically across the merchant and up to **8** extra recipients in a single transaction, "for platform fees, revenue sharing, referral commissions, and fee-payer cost recovery". <https://github.com/x402-foundation/x402/pull/3221> (merged 2026-10-26 20:39 UTC). Adapted from the splits model in the Solana Charge Intent draft (<https://paymentauth.org/draft-solana-charge-00.html>).
- **Mechanism:** the resource server lists `extra.splits` (absolute amounts in base units, not bps); the primary `payTo` gets the remainder, which must be > 0. Each leg must be a distinct on-chain transfer; split legs must match exactly, and any client overpayment goes to the merchant, never to a split recipient. Facilitators advertise `maxSplits` (absent = 0) and must reject requirements above it. Spec-only and SVM (Solana) first, with a network-agnostic note in `scheme_exact.md`; as of 2026-11-09 the SDK implementation (PR #3968, TS/Go/Python; last updated Nov 6) and Sui version (PR #4062) are still open.
- **Traction:** spec merged; no implementation released yet.
- **vs referralTree:** x402 can now pay a referral commission *inside* the payment, atomically, which closes the gap Split402 left (its MVP doesn't split atomically). But splits are flat, fixed amounts chosen by the merchant, with no tree, no decay, and a cap of 8 extra legs: fewer than a full depth-10 `rewardRoots` path plus the trigger. The natural integration is one split leg paying a referralTree contract (or LightForest group) that then fans out the multilevel share, so x402 carries the money and referralTree carries the rule.

### x402-mesh (StartupHub.ai)
- **What:** "open peer-pricelist + referral protocol for safe agentic commerce", MIT, by StartupHub.ai. Repo <https://github.com/StartupHub-AI/x402-mesh> (created 2026-05-23; v0.1 spec in `SPEC.md`; made rail-agnostic in commit `c9a70d2` on 2026-10-19; last push 2026-10-28; fetched 2026-11-16). Write-up: <https://www.startuphub.ai/ai-news/opinions/2026/x402-mesh-rail-agnostic> (Oct 21, 2026). Not previously tracked here; filed 2026-11-16 as a backfill.
- **Mechanism:** a vendor's `402 Payment Required` body carries a signed **peer menu** of competing offers in the same category. Each peer entry has an Ed25519-signed JWT referral token (`iss`, `aud`, `exp`, single-use `jti`, commission `cpct`, 5-minute TTL). If the agent picks a competitor and pays it, the competitor pays the referring vendor a commission (default **5%**, negotiable per token) and reports the redemption to a settlement endpoint. On x402 the reference rail is `MeshSplitter.sol`, a 2-way non-custodial splitter on Base: the agent approves USDC and calls `pay(jti, vendor, referrer, amount, commissionBps)`, which forwards vendor and referrer shares in one transaction and emits `MeshPaid(jti, …)` for reconciliation. Bindings for Stripe MPP / ACP (Connect `application_fee`), Google AP2 (terms inside the Payment Mandate) and L402. An optional `act_chain` claim carries delegation lineage (which agent paid, on whose behalf, referred by whom).
- **Traction:** 7 GitHub stars; npm `x402-mesh` has one version (0.1.0, published 2026-05-19) and 9 downloads in the month to 2026-11-15 (npm API); the repo publishes no deployed splitter address (only the Base USDC constructor args), and its contracts README says the on-chain side is inert until deployed. No public settlement numbers.
- **vs referralTree:** one hop, vendor-to-vendor ("every vendor is both a seller and a broker"), funded by the competitor that wins the sale. No tree, no decay, no graph. But it is the cleanest public example of a referral carried *inside the payment request* with atomic on-chain settlement, and of lineage (`act_chain`) riding with the token. For referralTree: the per-token `jti` + event-reconciled split is the shape an agent-facing `rewardRoots` trigger could take; and `act_chain` is the evidence an oracle would want before signing a multilevel payout to an agent acting for a principal.

### Related x402 affiliate experiments (not tracked in depth)
- Pyrimid (<https://pyrimid.ai>): pitched in March 2026 as an "affiliate payment router for x402 on Base" (vendor + affiliate + 1% protocol split; daydreams issue #684, 2026-03-26, <https://github.com/daydreamsai/daydreams/issues/684>). Looks dormant: the site returned `DEPLOYMENT_DISABLED` on 2026-11-16 and npm `@pyrimid/sdk` was last published 2026-03-29 (v0.2.6).
- x402aff (<https://github.com/MiroShark/x402aff>): routes x402 `payTo` to a per-builder 0xSplits contract (default 10% builder share).
- Toll402 bounty (<https://toll402.dev/bounty>): 30% of referred agent spend paid on-chain at settlement.
